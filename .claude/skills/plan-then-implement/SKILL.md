# Plan-then-Implement ワークフロー

## 適用判定（自動）
以下のいずれかに該当する依頼で発火:
- 3ファイル以上の編集が想定される
- 新機能追加・大幅リファクタ・データ移行・スキーマ変更
- 「設計して」「アーキテクチャを」「全体を」を含む依頼

該当しなければ通常実装で進めて良い。

## ステップ

### 1. インタビュー（要件不明瞭な時のみ）
要件が曖昧なら、実装に入らず以下を質問:
- 達成したいゴール（受入基準）
- 既存制約（互換性・パフォーマンス・依存）
- 期限・優先度
- 影響範囲を狭める／広げる方向性

### 2. Plan Mode（読み取り専用で調査）
Plan Modeに切替（Shift+Tab）してから:
- 関連ファイルをRead/Grepで把握
- 既存実装の前提・命名規約を抽出
- 影響範囲を列挙
- 計画書を書く（下記テンプレ）

### 3. 計画書テンプレ
```markdown
## ゴール
...（受入基準を1文）

## 影響ファイル
- src/foo.ts (変更)
- src/bar.ts (新規)
- tests/foo_test.ts (追加)

## 設計判断
- 案A: ...（採用）
- 案B: ...（不採用、理由：...）

## 実装ステップ
1. ...
2. ...

## 検証方法
- 単体テスト: tests/foo_test.ts
- 動作確認: $ npm run dev で /api/foo を叩く
- スクリーンショット: 該当UIなら必須

## ロールバック
- 失敗時: /rewind またはブランチ捨て
```

### 4. 実装（計画承認後）
- 計画通りに進める。逸脱が必要なら一旦止めて報告。
- 1ステップ完了ごとにcheckpointを意識（/rewind可能な状態を保つ）。

### 5. 自己検証（必須）
完了報告の前に:
- [ ] テスト全通過（test-runner subagentに依頼可）
- [ ] lint/format通過（hookで自動済のはず）
- [ ] UIなら描画確認（Chrome拡張 or Playwright）
- [ ] CLI/APIなら実行ログ
- 検証ログを実装報告に必ず添える

### 6. 報告フォーマット
```markdown
## 完了報告
- ゴール達成: ✓
- 変更ファイル: N件
- テスト: ✓ N pass / 0 fail
- 残課題: ...（あれば）
```
